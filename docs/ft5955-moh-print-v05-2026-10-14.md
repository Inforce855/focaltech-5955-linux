# FT5955 MOH v0.5: versioned host-template envelope — 14 October 2026

**Status:** experimental codec and integration scaffolding; **not** a functioning libfprint/fprintd driver.

## Context / confirmed v0.4 real-hardware baseline

An enrolled finger matched after exporting its proprietary MOH template, terminating the original isolated engine and importing that template into a second fresh sandbox. Other fingers tested returned `NO_MATCH`. This is an encouraging real-hardware same-finger/different-finger control, **not** measured authentication security or secure persistent storage.

## Prototype completed

The separate `ft5955-moh-print-v0.5` development package contains:

- `ft5955_print_codec.[ch]` — a portable C binary envelope for MOH template bytes, subfactor, USB VID:PID 2808:5955, algorithm ID and inverted-polarity version, bounded to 1 MiB with SHA-256 corruption detection.
- `print_codec.py` — an independent Python reference codec and synthetic cross-language test.
- `ft5955_fpi_print_bridge.[ch]` — **uncompiled** internal libfprint integration scaffolding, using `FPI_PRINT_RAW` plus the `fpi-data` GVariant property, for a host-matched (not on-chip) print.
- `fpprint_boundary_live.py` — an optional, explicitly authorised physical test that wraps and unwraps a versioned print envelope in supervisor memory between two isolated MOH engine processes, without saving biometric data.
- Five offline unit tests: format roundtrip; malformed metadata/bounds; C/Python compatibility; synthetic C engine restart and template reimport.

**Five synthetic tests passed** in the development environment. The GLib/FpPrint bridge has not yet been compiled against the user's isolated libfprint headers; the v0.5 live versioned-envelope path has not yet been run on the physical reader.

SHA-256 is only an accidental-corruption check: it provides **no confidentiality, authentication, anti-tamper guarantee or protection against template substitution**. Never treat this as an encryption/storage mechanism. No biometric files are written by the prototype.

## Intended next integration

1. Compile the new C codec and GLib/FpPrint bridge within `~/Projects/libfprint-ft5955` as an isolated dev build. Preserve the existing native FT5955 USB open/close path and existing MOH worktree.
2. Implement asynchronous fresh-touch acquisition and the 12-*accepted*-stage `FpDevice` enrolment callbacks; use `FPI_PRINT_RAW` for the versioned vendor template payload, leaving `device_stored=FALSE`.
3. Have verify/identify extract the validated print payload, import its template into a separately isolated engine process, then match a newly captured inverted 64×80 sample; correctly distinguish no match, poor quality, cancellation, corrupted record and engine errors.
4. Prove real libfprint `fp_print_serialize` / `fp_print_deserialize` against an isolated test. Examine encrypted at-rest storage, template isolation and permissions before using a system `fprintd` service.
5. Do not modify PAM, KDE authentication or the installed libfprint/fprintd stack until long-running and reboot-persistence tests and negative controls have succeeded.

This experiment is a step toward a **working proprietary-MOH-backed Linux driver**. The fully open-source end goal still requires independently implementing native matching.

## v0.5 real sensor result — 14 October 2026

The user completed a physical 12-accepted-impression enrolment using the versioned RAM-only print envelope, imported the validated template into a **fresh** MOH sandbox, and obtained verification responses `MATCH 1` and `NO_MATCH` over six live scans (three of each). The pasted terminal output did not label which finger was presented for each scan, so do not infer a false-reject rate or claim that every `NO_MATCH` was an impostor-control scan. The template was discarded at session end; this was not `FpPrint` serialisation or persistent storage.

## v0.6 standalone FpPrint roundtrip harness

The separate `ft5955-moh-libfprint-v0.6` development archive builds on the v0.5 C codec and includes strengthened driver/payload/type checks plus a standalone synthetic `FpPrint` serialisation test. Four portable codec unit tests passed locally. The new harness compiles against the user's **private** `libfprint-ft5955` source/compiled shared object and exercises `fp_print_serialize`/`fp_print_deserialize` without opening USB or invoking the vendor DLL. This actual-private-library step is **pending execution on Nobara** and must not be presented as completed. The source-tree driver enrol/verify callbacks, secure template storage, and fprintd integration remain unimplemented.
